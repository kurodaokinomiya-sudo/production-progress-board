# F02 AIメール取込の部分保存回復

現在も「1明細あればメール全体をスキップ」が成立することを確認して修正した。
既存のparsedJsonに `_mailBatch`（version/key/size/ordinal）を追加する最小案を実装前に報告した。列追加・新規キュー・既存データ移行は行わない。

- 文書/ページ/行から安定したsourceRefを作り、全候補の内容を正規化してSHA-256で取込単位を識別する。
- 一括writerで全件を事前検証してから保存し、保存後も全件の存在を確認する。
- 全statusの候補を参照するため、承認済み/却下済みを復活させない。ロック内で最新状態を再取得して不足分だけ保存する。
- 部分保存の再試行は再読取結果が同じ場合だけ不足分を追加する。結果が変わった場合は `AI_MAIL_REVIEW_REQUIRED` で停止し、無関係な明細を補充しない。
- 旧形式のメールは予定件数を復元できない。検索結果の `reviewRequired` と警告へ残し、「未取込なし」で隠さない。同じ検索範囲の独立した新規メールは処理を続けられる。

関連93テスト成功。保存前/途中/全件後/flush後の障害、応答消失、同時実行、AI応答の順序変更/内容変更、承認済み/却下済み、保存サイズ上限、文字列保存、従来の承認・重複・補完学習を検証した。Gmail/AIは合成fixtureだけを使用した。

残る制限: AIが再読取で異なる内容を返す場合と、旧形式の部分取込は自動復旧しない。後日許可された環境で、管理者がメール原本の明細数・sourceRef・候補status・承認済み案件を照合し、不足明細のみ通常の確認キューへ登録する必要がある。予定件数を推測した一括完了や既存候補の復活は行わない。
実Sheetsの部分書込と実GASの並行スケジューリングは未検証。スタブは書込途中終了と応答消失を明示的に模擬している。
