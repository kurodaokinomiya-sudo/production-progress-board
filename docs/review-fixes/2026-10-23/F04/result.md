# F04 注文・工程の競合復旧

古いversionを含む失敗フォーム全体が復元される指摘を再確認した。
編集開始時の値・自分の入力・最新の保存値を比較し、編集可能な項目だけを再適用する。未変更項目は最新値を使い、同一項目の衝突はフォーム内で「最新の保存値」「自分の入力」を選ぶまで保存できない。注文の非表示工程/ラベル設定も古い状態で上書きしない。
明確な競合は最新の取得完了後に復旧する。別案件の保存等でスナップショットを適用できなかった場合も、古い状態へversionだけを書き換えない。さらに更新された場合は通常のversion検査で再度拒否し、再比較する。

結果不明の再試行は、同じ入力なら元のpayload/requestIdを維持する。工程保存にも照合を追加し、末尾列 `processSaveJson` に直前のrequestIdと内容を記録する。新規キューや既存データ変換は行わない。直前の工程保存より後に別の工程保存が入った古い要求は、version競合として扱い、再適用しない。
作業員は工程専用APIの `id/version/stages/shippingStatus/requestId` だけを送る。権限・研磨条件・出荷条件は維持する。削除済み/消失した既存案件は復元から再作成せず、下書きを残して再保存を止める。アクセス失効時は下書きを消す。

関連57テスト成功（3値比較、同一項目、再競合、工程の保存後応答消失、保護された注文/ラベル項目、古いversion、削除/消失、既存の未保存確認/非同期保存/権限）。ビルド、コントラスト、diffチェック成功。
`npm run qa:conflicts` はソース版・生成物とも成功。注文・工程の別項目/同一項目、復旧中の再競合、作業員payload、保存済み応答消失、同じ新規注文の再試行、削除・失効を2タブと実localStorage保存/再読込で確認した。
共通デザイントークン、説明付きの選択欄、44px操作対象、復旧選択へのフォーカス、768pxのダイアログ内表示を確認した。`frontend-design` と最新のWeb Interface Guidelinesに沿って変更範囲を確認した。
