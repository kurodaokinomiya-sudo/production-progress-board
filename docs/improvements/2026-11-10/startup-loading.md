# 起動時・定期同期の読み込み軽量化

起動時に全案件・全取込履歴・材料在庫集計を一括取得していたため、処理済みの取込本文や材料履歴も待ち時間の増加要因になっていた。

## 変更

- 工程一覧など材料在庫以外の画面では `getSnapshot({ includeMaterials: false })` とし、材料履歴の読み込み・集計・そのためのロック待ちを省く。材料画面を開くと既存の専用APIで読み込み、表示中の定期同期では在庫も更新する。
- 取込キューは状態列を1回取得し、未処理行の本文・解析結果をまとめて取得する。離れた未処理行は最大8範囲にまとめ、Sheets呼び出しが行数に比例して増えないようにする。範囲の結合時に一部の処理済み行を読む場合も、返却前に状態を再確認して除外する。
- 状態空白の既存行、空行、日付・JSONの変換、読み込み中に承認された行に対応。取込の通常の全件読取APIは変更しない。
- 旧画面の `getSnapshot()` は材料在庫を含む従来の動作を維持する。権限の確認、保存処理、履歴の保存内容、表示・印刷仕様は変更しない。

編集元は `apps-script/Code.gs`、`apps-script/Repository.gs`、`src/app.js`。配布物の変更は `Code.gs`、`Repository.gs`、`Index.html` の3ファイルだけ。

## 検証

- 全932テスト成功、`node tools/contrast-audit.mjs` 成功。
- 処理済み10,000件＋未処理3件では、状態列10,003セルと未処理3行のみを取得。従来の本文・解析結果を含む10,003行の取得を避ける。これは合成データでの読取範囲の検証で、実際の起動秒数の測定ではない。
- 10,000行に未処理が交互に存在する場合も全文取得は8範囲以下。処理済みだけなら状態列のみを1回取得する。
- 起動・画面切替中の古い同期応答が新しい在庫取得を消さないこと、権限外の在庫取得を許可しないこと、旧クライアント互換性を検証。
- ローカル合成データでソース版・配布用ビルドの工程一覧起動、在庫画面への切替、在庫取得完了、キーボード操作、エラーなしをブラウザー確認。

## 残る増加要因

案件は終了・アーカイブ分も全件読み込み、研磨履歴や製品マスター照合も案件数に応じて増える。今回の変更で起動時間を一定にできるわけではない。取込の状態列も全行を走査する。材料画面を開いた際の履歴集計は残る。

さらなる対策は、終了案件の期間指定取得、変更分だけの同期、製品マスター照合の索引化など。これらは完成品一覧・配布表・研磨請求・重複判定・在庫投影に関わるため、今回の変更には含めない。実データの削除・過去履歴の移動は行っていない。
